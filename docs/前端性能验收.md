# 前端性能检查与验收

更新：2026-11-10。适用于当前 uni-app Vue 3 微信小程序前端。以下数值是项目初始目标，不是微信官方指标，也不是已测成绩。

## 当前证据和边界

- 已有类型检查、H5/微信编译、浏览器交互回归；这些检查不能证明真机帧率达标。目前是本地脚本，尚未配置 GitHub CI 自动门禁。
- 2026-11-10 上一轮微信预览包实测 1,945,840 字节；包大小必须按每次交付重新记录，不能用源码目录大小代替。
- 源码没有创建 Web Worker/微信 Worker，没有轮询型 setInterval；现有 setTimeout 用于首页转场和 Mock 延迟。不存在自行编写的多线程计算模块。
- 微信运行时负责逻辑层与视图层的运行和通信。异步请求、Promise、async/await 不等于创建计算线程；异步返回仍需处理重复操作、过期响应和页面退出。
- 尚未建立 iOS/Android 真机的启动、点击延迟、动画帧耗时、内存基线。现阶段每类一条演示数据，不能代表真实长列表和真实接口负载。

## 每次变更必做

1. 找到可重复操作，区分样式频闪、布局位移、图片重绘和真正的掉帧，不把所有问题都归因于性能。
2. 小改动运行相关用例；修改公共组件、布局或导航时运行完整回归。命令为仓库根目录的 `npm run check:mobile` 和 `npm run test:mobile`。
3. 对图片尺寸和重复资源、频繁响应式更新、重复导航、隐藏页面动画/定时器、未释放监听做代码检查。减少逻辑层与视图层之间不必要的数据传递；局部交互放在局部组件内。这与 [uni-app 官方性能建议](https://uniapp.dcloud.net.cn/tutorial/performance.html)一致。
4. 变更动画、手势或原生组件时，补微信真机同场景对比；没有真机结果时必须标注“待验收”，不得以浏览器通过代替。

## 真机测试与初始目标

至少覆盖一台 iPhone 和一台 Android 中低端设备，固定手机、系统、微信版本、基础库版本、构建版本、刷新率和网络条件。使用生产构建的开发预览；性能采样与屏幕录制分别运行，避免录屏本身影响采样。

| 场景 | 测量方法 | 初始目标/判定 |
| --- | --- | --- |
| 八宫格/卡片按压 | 同设备重复20次，记录触摸到首个可见反馈的时间 | P95 ≤100ms；不出现亮度闪变、白块和重复跳转 |
| 五个底栏往返 | 固定顺序切换20轮，记录帧耗时并观察布局 | 不重播整页入场位移；不得出现可见抖动/闪白；与基线比较首帧耗时 |
| 首页卡片展开 | 同卡片重复20次，微信性能工具采集帧耗时 | 60Hz设备以接近60fps为目标，重点检查超过50ms的长帧；连续长帧或超过100ms停顿必须排查，不以平均帧率掩盖卡顿 |
| 首次进入 | 同网络冷启动5次，记录到首屏主要内容可见的时间 | 初始目标中位数≤2秒，同时记录最大值；真实接口延迟与前端渲染耗时分开记录 |
| 连续进入/返回 | 分类→详情→播放→逐级返回20轮，比较稳定后的内存、页面栈 | 无页面栈残留，无随轮次持续增长的内存趋势；不能只比较一次前后瞬时内存 |
| 包和图片 | 微信预览打包报告、资源清单 | 当前主包项目预算2MiB，接近预算先评估非首屏分包；不是宣称平台上限为2MiB |
| 后续真实列表 | 至少100条数据及弱网、失败、空结果 | 分页；必要时虚拟列表；滚动不卡住、失败不重置已加载内容 |

目标不达成时先记录设备和数据，再定位、修改、用相同条件复测。只有测量证据支持时才引入 Worker；重计算可评估 Worker，但它不能直接修复 CSS 频闪、布局位移或平台导航过渡。

## 本轮频闪处理

八宫格使用只缩放、不改变透明度的反馈；导航期间用 `busy` 逻辑锁拦截重复激活，不触发原生 `disabled` 外观切换。保留鼠标、键盘、触摸取消和减少动画支持。测试覆盖按住/松开亮度不变、导航锁定背景不变、连续点击只导航一次。真机结果待补。
